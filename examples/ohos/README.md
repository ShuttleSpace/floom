# Floem on OpenHarmony (HarmonyOS) — example app shell

This directory is a **scaffold** for running a Floem app on OpenHarmony. It is
the application-shell counterpart to the OHOS backend that lives inside the
`floem` crate (`src/embedder/ohos.rs`, `src/platform/{ohos_bridge,…}.rs`,
`src/accessibility/backend_ohos.rs`).

## What lives here

- `src/lib.rs` — the Rust entry (cdylib). On OHOS it invokes
  `tgui_winit_ohos::export_ohos_winit_app!(ohos_factory)`, which generates the
  `ohos_winit_runtime_*` C-ABI symbols that the ArkTS layer drives. The factory
  builds a `floem::Application` with one window (`app_view`).
- `entry/src/main/ets/FloemBridge.ets` — the ArkTS side that registers the
  shared N-API bridge (`register_platform_bridge`) and implements every method
  floem *pulls* (getText/setText via `@kit.BasicServicesKit`, openUrl via
  `startAbility`, openFile/saveFile via `@kit.CoreFileKit` picker, show/hide
  keyboard via `@kit.IMEKit`, setAccessibilityTree for a11y). It also forwards
  picker / share / accessibility / IME results back into Rust via the `on_*`
  napi exports.
- `entry/src/main/ets/EntryAbility.ets` — the Stage-model `UIAbility` that calls
  `setAppContext(this.context)` + `registerPlatformBridge()` at
  `onWindowStageCreate`, and forwards share intents (`onCreate`/`onNewWant`) into
  `onSharedFiles`. Register it in `module.json5`.

## How the two sides connect

```
 ArkTS (EntryAbility.ets onWindowStageCreate)
        │  setAppContext(ctx) + registerPlatformBridge()
        ▼
 floem.register_platform_bridge({ getText, setText, openUrl,
                                   openFile, saveFile, setAccessibilityTree,
                                   showKeyboard, hideKeyboard })
        │  Rust pulls these via N-API (call_bridge)
        ▼
 floem core ◄── ArkTS pushes results via napi exports:
                  on_file_picked / on_shared_files / on_accessibility_action /
                  on_ime_commit / on_ime_preedit / on_ime_composition_end /
                  on_ime_delete
        │
        ▼  (runtime entry, C-ABI)
 ohos_winit_runtime_*  (generated by export_ohos_winit_app!)
        │
        ▼
 tgui-winit-ohos  →  floem-winit-core ApplicationHandler (shared trait)
```

The ArkTS side imports the napi module as `import * as floem from 'libohos.so'`
(the cdylib name). Change the import if `cargo-ohos-app` emits a different
module id.

## Building & running

The Rust crate is packaged as a `cdylib` and linked into an OHOS Stage model
Ability by [`cargo-ohos-app`](https://crates.io/crates/cargo-ohos-app). The
crate is named `ohos`, so it produces `libohos.so` — align the Ability's load
name / `cargo-ohos-app` config accordingly (the upstream tooling assumes
`libentry.so`; rename the crate or configure the loader if needed).

```bash
# From this directory (or the floem workspace root):
cargo ohos --target aarch64-unknown-linux-ohos
# Then open / sync the generated OHOS project in DevEco Studio and run on a
# device or the emulator (x86_64 for the simulator).
```

### macOS note

`cargo-ohos-app`'s `discover_hvigor` hard-codes `hvigorw.bat` (Windows-only),
so on macOS/Linux you must apply the `harmony-app-rs-patch` that looks for the
extension-less `hvigorw` wrapper. See `docs/ohos.md` (OHOS packaging section).

## Known gaps (as of 2026-08-12)

1. **`floem::Application` `Send` gate — RESOLVED.** `tgui-winit-ohos`'s
   `RuntimeApplication` required `ApplicationHandler + Send`, but `Application`
   is deliberately `!Send` (its `Rc`-backed signals and `Box<dyn Fn>`
   callbacks). The gate was cleared by **relaxing the fork, not floem**:
   `RuntimeApplication` now drops `+ Send` in
   `tgui-winit-ohos-fork/src/ffi.rs`. This is safe because the fork's
   `runtime_new` creates the `ApplicationHandler` *inside* its worker thread via
   `AppFactory` — the handler never crosses a thread boundary, only the `Send`
   `EventLoop` does. Note also there was a misdiagnosis to avoid: floem's
   `ApplicationHandler` **does** unify with the fork's, because `floem-winit`
   re-exports `floem-winit-core`'s `ApplicationHandler` and `floem-winit-core`
   is a single shared instance used by both crates. The example now compiles:
   `cargo check -p ohos --target aarch64-unknown-linux-ohos` → **0 error**.
   (The other half of the original failure — `main` not found — was fixed by
   making this crate a `cdylib` via `[lib] crate-type = ["cdylib"]`.)
2. **Real `cargo build` (link) gate.** `cargo check` passes; linking still needs
   an OHOS fontconfig sysroot and the wgpu Vulkan `VK_OHOS_surface` loader.
3. **ArkTS bridge implemented (2026-08-13).** `FloemBridge.ets` now calls real
   OHOS Kit APIs (clipboard via `@kit.BasicServicesKit`, external URL via
   `startAbility`, file picker via `@kit.CoreFileKit`, IME show/hide via
   `@kit.IMEKit`), and `EntryAbility.ets` wires the lifecycle + share intents.
   It is **not yet compiled in DevEco** (no OHOS SDK/typecheck in this
   environment) — verify against your SDK before shipping. Two integration
   points still need device validation:
     - **Accessibility provider**: `setAccessibilityTree` stores floem's
       neutral tree; mapping it to native OHOS Accessibility Kit nodes and
       forwarding `onPerformAction` → `on_accessibility_action` must be
       completed in an `AccessibilityProvider` (see the TODO in
       `FloemBridge.ets`).
     - **IME for a native window**: `showKeyboard`/`hideKeyboard` use
       `InputMethodController`; for a winit window with no focused ArkTS input
       the keyboard visibility is best driven by an Input Method Extension.
4. **No real-device screen-reader / IME integration test** has been run.
