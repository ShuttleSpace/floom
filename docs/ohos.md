# OpenHarmony (HarmonyOS) backend

Experimental support for running floom on OpenHarmony / HarmonyOS, added as an
embedder backend (no fork of floom core). Status: **compiles and runs on the
DevEco emulator.** `cargo check` / `cargo build` are clean for `floom` +
`examples/ohos` on `aarch64-unknown-linux-ohos`; the arm64-v8a HAP starts,
renders and responds to taps (see `docs/gates/ohos.md` gate 1); and the ArkTS
platform bridge is DevEco-compiled and actually reached from Rust on-device
(2026-09-27) — floom's N-API exports are merged into `libentry.so`, and every
bridge call from the event-loop worker thread is marshalled onto the JS thread
(see "N-API wiring"). Runtime font fallback (`ohos_font.rs`)
is implemented and verified to *type-check* on the real OHOS toolchain but
**UNVERIFIED on-device**. The ArkTS accessibility layer (`FloomA11y.ets`) was
re-audited for #113 and found to use an **API that does not exist** in
`@kit.AccessibilityKit` (no `registerProvider` / `AccessibilityNodeInfo` /
`AccessibilityRole` / `ActionType` / `AccessibilityState` / `invalidate`); the
real screen-reader exposure for a native window is the **native C**
`ArkUI_AccessibilityProvider` (task #121). `FloomA11y.ets` is now a
type-correct reference seam and no longer references any non-existent symbol.
Linking (`cargo build` → HAP) and the render gate are done; what remains is
on-device a11y / IME / clipboard / file-picker *validation* (the native a11y path
is code-complete via #121 + #122 Route A, but still UNVERIFIED on-device).

## Architecture

```
            ArkTS XComponent shell (generated by cargo-ohos-app)
                          │  surface / focus / frame / touch / mouse / key
                          ▼
                 floom-winit-ohos  (OHOS event loop + windowing)
                          │  pumps winit WindowEvents
                          ▼
        floom::app::Application  (impl ApplicationHandler)
                          │
            ┌─────────────┴──────────────┐
            ▼                            ▼
   floom renderer (wgpu, VK_OHOS_surface)   floom view tree / reactivity
                          │
                  N-API bridges (clipboard / file / URL / share)
```

Flow:

1. `cargo-ohos-app` packages the Rust `staticlib` into a Stage Model HAP and
   generates an ArkTS `XComponent` shell.
2. `floom-winit-ohos` owns the OHOS event loop, translates native input into
   standard winit `WindowEvent`s, and drives an `ApplicationHandler`.
3. floom's `Application` (which implements `floem-winit-core`'s
   `ApplicationHandler`) is that handler — wired in the app shell via
   `export_ohos_winit_app!(ohos_factory)` (see `examples/ohos/src/lib.rs`).
   `floom_app_factory()` in `crates/floom/src/app/mod.rs` is a convenience stub that returns
   an `Application` with **no** window; real apps must supply their own factory
   that also calls `.window(...)`.
4. The renderer draws through wgpu's `VK_OHOS_surface` (wgpu ≥ 0.30, Vulkan
   backend).

## The blocker (and its resolution)

There were **two** compile gates, and the first is easy to misdiagnose.

### Gate 1 — `ApplicationHandler` unification (resolved by the retarget)

floom's `Application` implements **`floem-winit-core`**'s `ApplicationHandler`
(`floom` renames the `floem-winit` crate as `winit` in source, see
`Cargo.toml:65`). `floom-winit-ohos` requires `RuntimeApplication:
floem_winit_core::application::ApplicationHandler + Send`.

**Important correction:** this is *not* a "two distinct crates don't unify"
problem. `floem-winit` (the facade floom depends on) **re-exports**
`floem-winit-core`'s `application::ApplicationHandler`, and `floem-winit-core`
is a **single shared crate instance** used by both `floem-winit` and
`floom-winit-ohos` (see `Cargo.lock`: `floem-winit` depends on `floem-winit-core`,
and the fork depends on the very same `floem-winit-core` package). So the
`ApplicationHandler` bound is satisfied — the two traits unify through
`floem-winit-core`. The drift between upstream `winit_core 0.31.0-beta.2` and
`floem-winit-core` is near-zero (byte-identical `ApplicationHandler`, the OHOS
backend uses only the unchanged subset), so the retarget (`winit_core → floem_winit_core`
rename; see `crates/vendor/floom-winit-ohos/patch/retarget-to-floem-winit-core.patch`) is
mechanical and the method set (`can_create_surfaces` / `window_event` /
`about_to_wait` / `proxy_wake_up` / `destroy_surfaces`) already matches.

That "single shared crate instance" claim was **not** actually true until
2026-09-18: `crates/vendor/floom-winit-ohos` pinned `floem-winit-core` and `dpi` to the
**git** rev, while the patched `floem-winit` facade uses the vendored **path**
copies. Cargo treats different sources as different packages, so the resolve
graph held two `floem-winit-core` and three `dpi` instances, and the OHOS backend
required a different `ApplicationHandler` than the one `floom::Application`
implements. The `[patch."https://github.com/lapce/winit"]` entry in the root
`Cargo.toml` now redirects every member (`floem-winit`, `floem-winit-core`,
`dpi`) at the vendored tree, which is what makes the unification real. Only an
OHOS target can observe this, which is why macOS never caught it.

### Gate 2 — the `Send` bound (resolved by relaxing the fork)

After the retarget, the *only* remaining error is that `RuntimeApplication`
requires `Send`, but `floom::Application` is deliberately **`!Send`**:

- `Application.event_loop: Option<floem_winit::event_loop::EventLoop>` carries
  `PhantomData<*mut ()>` and platform backends (e.g. wayland's `Rc<LoopInner>`);
- `ApplicationHandle.event_listener: Option<Box<dyn Fn(AppEvent)>>` (no `Send`);
- window/timer/drag state holds `Rc<…>`-backed signals (`RwSignal<Size>` uses
  `UnsyncStorage = Rc<()>`), `Rc<dyn Any>`, `Box<dyn Fn()>` menu callbacks, etc.

Forcing `Application: Send` would mean making floom's whole reactivity layer
`Sync`/`Send` (signals would need `SyncStorage`), which fights floom's
intentionally single-threaded design — a sweeping, risky change.

**Resolution — relax the fork, not floom:** `floom-winit-ohos`'s
`runtime_new` spawns a worker thread and creates the `ApplicationHandler`
**inside** that thread via `AppFactory`; the handler never crosses a thread
boundary (only the `Send` `EventLoop` is moved into the worker). So the `Send`
bound was defensive and unnecessary. `crates/vendor/floom-winit-ohos/src/ffi.rs` now
defines `pub trait RuntimeApplication: ApplicationHandler {}` (no `+ Send`),
with a comment explaining the safety argument. After this change,
`examples/ohos` compiles:

```sh
cargo check -p ohos --target aarch64-unknown-linux-ohos   # Finished, 0 error
```

(7 benign warnings come from the floom lib — desktop `translate.rs` dead-code
and `private_interfaces` — and are unrelated to OHOS.)

## N-API platform bridge (unified)

OpenHarmony exposes OS services (pasteboard, file picker, browser, share) only
through ArkTS. The Rust side reaches them by exporting N-API functions that
ArkTS calls to **register** a capability object, then calling **back** into that
object on demand. All four bridges share one registration entry point — see
`crates/floom/src/platform/ohos_bridge.rs`:

- `#[napi] register_platform_bridge(env, bridge)` — ArkTS calls this once at
  startup with a single object that wraps every capability. Rust stores it as a
  type-erased `napi::Ref<()>` (so the ArkTS object is not GC'd) and keeps the
  `Env` for later callbacks.
- `call_bridge(f)` — runs `f(env, bridgeObject)` if a bridge is registered, else
  returns `None`. Every concrete bridge (`ohos_clipboard` / `ohos_external` /
  `ohos_file` / `ohos_receive`) is just a thin caller over `call_bridge`.

Pull (Rust → ArkTS) diagram — clipboard shown; file/external/share use the same
shape with a different method name (`openUrl` / `openFile` / `saveFile`):

```
 ArkTS (pasteboard/file/url/share)     Rust (floom → libentry.so)
 ┌───────────────────────┐            ┌──────────────────────────────┐
 │ floomBridge = {       │ register   │ #[napi]                       │
 │   getText/setText,    │ ─────────▶ │ register_platform_bridge(obj)  │
 │   openUrl, openFile,  │            │   → napi::Ref<()> + Env        │
 │   saveFile }          │            └──────────────┬───────────────┘
 └───────────────────────┘                          │ get_contents()/open_url()/…
                                                   │   call obj.getText() via N-API
 ┌───────────────────────┐            ┌─────────────▼─────────────────┐
 │ returns result/null   │ ◀───────── │ func.call("getText", ...)       │
 └───────────────────────┘            └───────────────────────────────┘
```

Push (ArkTS → Rust) — the reverse direction, used by the two async bridges:

- `on_file_picked(request_id, uris)` (`ohos_file.rs`) — ArkTS invokes this after
  the `@ohos.file.picker` resolves; it matches `request_id` to the pending
  callback and builds a `FileInfo`.
- `on_shared_files(uris, mime_types, display_names)` (`ohos_receive.rs`) —
  ArkTS invokes this from `Ability.onCreate(want)` / `onNewWant(want)` with the
  shared URIs; it feeds the registered `set_shared_files_handler`.

The **canonical** ArkTS implementation is
`examples/ohos/ohos-app/entry/src/main/ets/FloomBridge.ets` (DevEco-compiled and
exercised on the emulator; `examples/ohos/entry/src/main/ets/FloomBridge.ets` is
a byte-identical reference copy). The N-API module import is
`import floom from 'libentry.so'` — napi-rs never calls `napi_module_register` on
OHOS, so floom's exports are merged into the HAP's one registered N-API module
(see "N-API wiring"). Simplified sketch of the bridge object:

```typescript
// entry/src/main/ets/FloomBridge.ets
import floom from 'libentry.so';
import { pasteboard } from '@kit.BasicServicesKit';
import { picker } from '@kit.CoreFileKit';

// NOTE: openFile / saveFile receive (requestId, options) — Rust fires the
// picker and expects ArkTS to call back floom.onFilePicked(requestId, uris).
export function registerPlatformBridge(): void {
  floom.registerPlatformBridge({
    getText(): string | null {
      return pasteboard.getSystemPasteboard().getDataSync().getPrimaryText() || null;
    },
    setText(text: string): void {
      const pb = pasteboard.getSystemPasteboard();
      pb.setData(pasteboard.createData(pasteboard.MIMETYPE_TEXT_PLAIN, text));
    },
    openUrl(url: string): void {
      // appContext.startAbility({ action: wantConstant.ACTION_VIEW, uri: url })
    },
    openFile(requestId: number, options: object): void {
      new picker.DocumentViewPicker().select()
        .then((uris) => floom.onFilePicked(requestId, uris))
        .catch(() => floom.onFilePicked(requestId, null));
    },
    // saveFile(requestId, options) similar, using DocumentSavePicker.
  });
}
```

The Rust side: `ohos_bridge.rs` exports `register_platform_bridge` and the
`call_bridge` helper; `ohos_clipboard.rs` / `ohos_external.rs` / `ohos_file.rs`
/ `ohos_receive.rs` each perform their capability-specific calls (and, for the
async ones, expose the `on_file_picked` / `on_shared_files` N-API entry points
that ArkTS calls back into).

### IME (soft-keyboard) bridge — `crates/floom/src/platform/ohos_ime.rs`

OHOS has no winit IME, exactly like iOS, so floom drives the soft keyboard
through the shared N-API bridge. The flow is bidirectional:

- **Rust → ArkTS** (`set_keyboard_visible`): called from
  `WindowHandle::process_update_message` on `SetImeAllowed` (text field gains /
  loses focus). It invokes `showKeyboard()` / `hideKeyboard()` on the registered
  bridge object.
- **ArkTS → Rust** (text edits): the ArkTS input-method extension pushes edits
  into a global queue via these `#[napi]` exports (they mirror `ios_ime.rs`):
  - `on_ime_commit(text: string)` → `ImeEvent::Commit`
  - `on_ime_preedit(text: string, cursorStart: number, cursorEnd: number)` →
    `ImeEvent::Preedit` (negative cursors ⇒ no cursor)
  - `on_ime_composition_end()` → `ImeEvent::Disabled` (matches the established
    "composition end" semantics in `embedder/window_ext.rs`)
  - `on_ime_delete(before: number, after: number)` → `ImeEvent::DeleteSurrounding`

  The queue is drained once per frame from `WindowHandle::process_update_no_paint`
  (right after the accessibility-action drain) and injected as `Event::Ime`, so
  composed / committed text reaches `text_input` views through the same path as
  the desktop winit IME.

ArkTS side (add `showKeyboard` / `hideKeyboard` to the bridge object and wire
the input-method extension to call the `on_ime_*` exports — see the canonical
`FloomBridge.ets`):

```typescript
// inside the object passed to register_platform_bridge:
showKeyboard(): void {
  inputMethod.getInputMethodController().showTextInput();
}
hideKeyboard(): void {
  inputMethod.getInputMethodController().hideTextInput();
}
// input-method extension / TextInput onCommit / onPreEdit →
//   floom.on_ime_commit(text)
//   floom.on_ime_preedit(text, start, end)
//   floom.on_ime_composition_end()
//   floom.on_ime_delete(before, after)
```

> **Single-window assumption:** the IME queue (and the accessibility-action
> channel) is a single global, matching OHOS's current single-`Window` model.
> If OHOS ever supports multiple windows, both must become per-window — see
> "Single-window assumption" below.
>
> **Cursor area / purpose forwarded (#112, 2026-08-13):** `SetImeCursorArea`
> (caret rect) and the new additive `SetImePurpose { purpose: ImePurpose }`
> update message now flow to ArkTS:
> - `WindowHandle::process_update_message` `SetImeCursorArea` arm (`target_env="ohos"`)
>   calls `ohos_ime::set_ime_cursor_area(x, y, w, h)` → bridge `updateImeCursorArea`
>   → `inputMethod.getInputMethodController().updateCursor({ left, top, right, bottom })`.
> - `SetImePurpose` (new, additive) → `ohos_ime::set_ime_purpose(purpose)` → bridge
>   `updateImeConfig(purpose)` (purpose encoded as an `i64` discriminant:
>   `0 Text, 1 Password, 2 Number, 3 Email, 4 Url, 5 Search`). The ArkTS side
>   stores it (`currentImePurpose`) for the IME extension / a focused ArkTS input.
> - `set_keyboard_visible` (visibility) is unchanged; `updateImeConfig` is best-effort
>   on a native (winit) window because OHOS `InputAttribute.textInputType` is decided
>   at `attach` time (driven by the IME extension, not the app).
> Both new Rust funcs are gated `target_env="ohos"` and verified to compile on the
> real OHOS toolchain (`cargo check -p floom --target aarch64-unknown-linux-ohos`,
> 0 errors). The exact `Cursor` field shape (`left/top/right/bottom` vs
> `left/top/width/height`) and whether `updateCursor` actually repositions the
> candidate panel on a winit window are **on-device verification items (#113)**.
>
> **Widget-level purpose emission done (#112, 2026-08-13):** `TextInput` now
> carries an `input_purpose: ImePurpose` field (default `ImePurpose::Text`,
> overridable via the `TextInput::input_purpose(...)` builder) and emits
> `set_ime_purpose(self.input_purpose)` when it gains focus (right after
> `set_ime_allowed(true)`). On OHOS this reaches `ohos_ime::set_ime_purpose` →
> `updateImeConfig`; on every other backend `SetImePurpose` has no handler, so
> the call is a harmless no-op and desktop keeps hard-coding `ImePurpose::Normal`
> via `SetImeAllowed`'s `ImeRequestData`. `TextEditor` also emits purpose on focus
> gain via the `EditorView::input_purpose(...)` builder (stored in a `RwSignal`
> so a later builder call is observed at event time).

### N-API wiring (resolved, verified on-device 2026-09-27)

- Dependencies are `napi = "2"` / `napi-derive = "2"` with no `napi_build::setup()`
  step. napi-rs 2.x's `#[napi]` codegen registers each export through a `#[ctor]`
  in the cdylib's `.init_array`, which only runs if the `.so` is dlopen'd *and*
  something calls its `napi_register_module_v1`.
- The module-registration collision was the original blocker: napi-rs never calls
  `napi_module_register` on OHOS, so `import … from 'libohos.so'` resolved to the
  wrong module and every floom export came back `undefined`. An OHOS HAP links a
  single N-API module, so `entry/src/main/cpp/napi_init.cpp`'s `Init` now ends
  with `napi_register_module_v1(env, exports)`, letting libohos.so fill in the
  same `exports` object `libentry.so` is registering. ArkTS therefore imports
  floom from `'libentry.so'`, and the declaring pair is
  `entry/src/main/cpp/types/libentry/{index.d.ts,oh-package.json5}` — the
  `types/libohos/` copy is gone.
- napi-rs renames every Rust `snake_case` export to `camelCase` for JS, so ArkTS
  calls `registerPlatformBridge` / `onFilePicked` / `onSharedFiles` /
  `onAccessibilityAction` / `onImeCommit` / `onImePreedit` /
  `onImeCompositionEnd` / `onImeDelete`. The winit C-ABI entry
  (`ohos_winit_runtime_*`) is unaffected and still goes through `libentry.so`.
- **Threading — why bridge calls are marshalled.** N-API values belong to the JS
  thread: `napi_call_function` from any other thread aborts with `Fatal: ecma_vm
  cannot run in multi-thread!`. floom's OHOS runtime drives the event loop from a
  *worker* thread (`floom-winit-ohos`'s `runtime_new` bootstraps the loop on the
  calling — JS — thread, then moves it into `thread::spawn`), and every bridge
  call (clipboard, file picker, external URL, IME, a11y) originates there.
  `crates/floom/src/platform/ohos_bridge.rs` therefore creates a thread-safe function at
  registration time; `call_bridge` either runs inline (already on the JS thread)
  or posts the closure and waits on a `Condvar` for the JS thread's result,
  degrading to `None` after a 5 s timeout. The a11y debug feed confirms the
  round trip: hilog shows `[floom] a11y tree updated: {…}` with the real
  serialized tree, logged from the **JS** thread, and 0 occurrences of the
  multi-thread abort.
- **Packaging — the HAP must actually contain `libohos.so`.** The bridge's
  `entry/src/main/cpp/CMakeLists.txt` links the Rust runtime as a *shared* library
  (`add_library(ohos_runtime SHARED IMPORTED)`), so `libentry.so` records
  `DT_NEEDED libohos.so` and the loader resolves it from
  `/data/storage/el1/bundle/libs/arm64/`. hvigor packages the CMake build
  outputs *plus* prebuilt `.so` files under `entry/libs/<abi>/` — so the freshly
  built runtime must be copied to `entry/libs/arm64-v8a/libohos.so` before
  `assembleHap`. A `clean` + `assembleHap` is **green even when the file is
  missing** (the build only compiles/packs; nothing checks the `DT_NEEDED`
  closure), which yields a HAP that installs and then dies at load with no
  rendering. Verify with `unzip -l entry/build/default/outputs/default/
  entry-default-unsigned.hap | grep libohos` (expected ≈ 43.9 MB HAP for a debug
  build). The two locations must be the **same** build: linking reads
  `entry/src/main/cpp/libs/arm64-v8a/libohos.so`, packaging reads
  `entry/libs/arm64-v8a/libohos.so`; having both present from *different* builds
  raises hvigor's `ProcessLibs … Duplicated files found in module entry`.
- This code is compiled **only** for `target_env = "ohos"` (not `target_os =
  "ohos"` — the OHOS standard target is `target_os = "linux"`, `target_env =
  "ohos"`), so the host build is unaffected. **Verified 2026-08-12**: `cargo
  check -p floom --lib --target aarch64-unknown-linux-ohos` passes 0 error on
  the real DevEco SDK (`/Applications/DevEco-Studio.app/Contents/sdk`).

## Accessibility bridge

> **#113 verification result (2026-08-13) — the original design is INVALID.**
> The ArkTS side (`FloomA11y.ets`) was written against an OHOS Accessibility
> Kit API that **does not exist**:
> - `@kit.AccessibilityKit` / `ets/api/@ohos.accessibility.d.ts` exports **no**
>   `registerProvider`, `AccessibilityNodeInfo`, `AccessibilityRole`,
>   `ActionType`, `AccessibilityState`, or `invalidate`. (Verified by grepping
>   the entire SDK `ets/api` tree — those symbols appear nowhere, except
>   unrelated `registerProvider` in `huksExternalCrypto` and a different
>   `ActionType` in `multimodalInput`.)
> - ArkTS **cannot** register an accessibility provider at all. A native
>   (winit) window can only expose a screen-reader tree through the **native C**
>   API in
>   `native/sysroot/usr/include/arkui/native_interface_accessibility.h`:
>   `ArkUI_AccessibilityProvider`, `ArkUI_AccessibilityElementInfo`
>   (`SetElementId` / `SetParentId` / `SetAccessibilityText` /
>   `SetAccessibilityDescription` / `SetScreenRect` / `SetOperationActions` /
>   `SetClickable` / `SetFocusable` / `SetChecked` / …),
>   `ArkUI_Accessibility_ActionType` (CLICK=0x10, LONG_CLICK=0x20,
>   GAIN_ACCESSIBILITY_FOCUS=0x40, SCROLL_FORWARD=0x100, SET_TEXT=0x4000, …),
>   registered via `OH_ArkUI_AccessibilityProviderRegisterCallback` /
>   `…WithInstance`.
> - The OHOS example is a **native Rust/winit window**: `EntryAbility` does NOT
>   load an ArkUI page (`pages/Index` is commented out). There is therefore no
>   ArkUI component tree for an `.accessibility*` overlay to attach to either.
>
> Consequence: the `AccessibilityProvider` implementation in `FloomA11y.ets`
> (task #111) was **completed against a fictional API** and cannot work. It has
> been replaced by a type-correct reference seam (`roleToComponentType`,

> **#121**: rework `crates/floom/src/accessibility/backend_ohos.rs` to call the native C

### Status (2026-08-13, #121 implemented)

The native C provider wrapper is **implemented** in
`crates/floom/src/accessibility/backend_ohos_native.rs` (`#![cfg(target_env = "ohos")]`,
links `libace_ndk.z`):

- `extern "C"` bindings to every `OH_ArkUI_AccessibilityElementInfoSet*` /
  `OH_ArkUI_AddAndGetAccessibilityElementInfo` / `…ProviderRegisterCallback` /
  `OH_ArkUI_SendAccessibilityAsyncEvent` used by the bridge.
- `ArkUI_AccessibilityProviderCallbacks` is filled with Rust callbacks
  (`cb_find_by_id`, `cb_find_by_text`, `cb_find_focused`,
  `cb_find_next_focus`, `cb_execute_action`, `cb_clear_focus`,
  `cb_cursor_position`). The a11y service invokes these on **its own thread**,
  so a thread-safe `Snapshot` (a `Mutex<AccessTree>` clone + a bidirectional
  Floom-`u64` ↔ native-`i32` id map) is kept behind a `OnceLock` and updated
  from `update_tree`.
- `update_tree` now (1) applies the diff, (2) `update_snapshot(&self.tree)`,
  (3) `notify_content_update()` (sends `PAGE_CONTENT_UPDATE` to prompt a
  re-query), and (4) keeps the ArkTS `setAccessibilityTree` push as a debug
  feed.
- `cb_execute_action` maps `ArkUI_Accessibility_ActionType` → neutral
  `AccessAction` (SET_TEXT extracts its `text` argument) and forwards it to the
  existing `ACTION_TX` channel — same path the old `#[napi]`
  `on_accessibility_action` used.

```
WindowState::update_accessibility_tree()          (every committed frame)
   └─ OhosAccessibilityBackend::update_tree(update)
        └─ AccessTree::apply  +  update_snapshot  +  notify_content_update()
                                       │ (Snapshot behind Mutex, read by a11y thread)
        └─ call_bridge → setAccessibilityTree(tree)   # debug feed only
   ── OHOS accessibility service thread ──
   OH_ArkUI_AccessibilityProviderRegisterCallback(provider, callbacks)
      callbacks.findAccessibilityNodeInfosById / ByText / findFocused / findNextFocus
         → build ArkUI_AccessibilityElementInfo from Snapshot
      callbacks.executeAccessibilityAction(nodeId, actionType, …)
         → ACTION_TX.send((floom_id, AccessAction, payload))
```

### Status (2026-08-13, #122 implemented — Route A)

#122 is **implemented** via the minimal, broadly-supported route. The OHOS NDK
exposes `OH_NativeXComponent_GetNativeAccessibilityProvider(component, &provider)`
(`ace/xcomponent/native_interface_xcomponent.h`, **API 13**). The winit fork
(`floom-winit-ohos`) already holds the `OH_NativeXComponent*` for the window and
exposes it via `WindowExtOhos::xcomponent_ptr()`; the XComponent is the rendering
surface the app draws into, so the accessibility service traverses it directly —
**no custom ArkUI node and no window-tree mount are required**.

Wiring (all `#[cfg(target_env = "ohos")]`):

- `crates/floom/src/app/handle.rs` — at window creation, reads
  `tgui_winit_ohos::WindowExtOhos::xcomponent_ptr()` off the winit `Window` and
  threads it into `WindowHandle::new` as an `xcomponent` parameter (mirrors the
  iOS `ui_view` plumbing).
- `crates/floom/src/window/handle.rs` — after attaching the `OhosAccessibilityBackend`, calls
  `crate::accessibility::backend_ohos::attach_xcomponent_provider(xcomponent)`
  (null-safe no-op if the pointer is not yet available).
- `crates/floom/src/accessibility/backend_ohos.rs` — `attach_xcomponent_provider` (safe
  wrapper) → `backend_ohos_native::register_native_provider_for_xcomponent`,
  which casts to `*mut OH_NativeXComponent`, calls
  `OH_NativeXComponent_GetNativeAccessibilityProvider`, and on success calls
  `register_native_provider` (the same callback registration as #121).
- `crates/floom/src/accessibility/backend_ohos_native.rs` — opaque `enum OH_NativeXComponent {}`,
  the `OH_NativeXComponent_GetNativeAccessibilityProvider` `extern "C"` binding
  (in the existing `#[link(name = "ace_ndk.z")]` block), and
  `register_native_provider_for_xcomponent`.

Result: at window creation the OHOS screen reader obtains Floom's `AccessTree`
through the registered callbacks — the same `Snapshot` / `ACTION_TX` plumbing #121
built. The cross-compile `cargo check` passes 0 error.

> **Route B (superseded):** the original #122 plan mounted an `ARKUI_NODE_CUSTOM`

> `OH_ArkUI_NativeModule_GetNativeAccessibilityProvider` (API 23). That is

### Build wiring notes

- The native accessibility lib is linked via `#[link(name = "ace_ndk.z")]`; the
  example's OHOS build must place `libace_ndk.z.so` on the link search path
  (the NDK sysroot `usr/lib/<target>/` provides it). `cargo check` does not
  link, so this is only exercised at `cargo build` / HAP packaging time.
- The a11y `#[napi]` entry points (`setAccessibilityTree` on the shared bridge
  object and the free `on_accessibility_action`) coexist with the native C
  provider; both are compiled behind `target_env = "ohos"`.
- `update_tree` pushes the snapshot unconditionally today (cheap: a clone +
  Mutex write); a future optimization can diff `AccessTreeUpdate::is_empty()`
  to skip `notify_content_update` when nothing changed.
- Single-window assumption: the reverse action channel is one global sender
  (`ACTION_TX` in `backend_ohos.rs`); multi-window OHOS apps would need
  per-window routing.

## Runtime font discovery (#115)

**Implemented 2026-08-13; verified on the real OHOS toolchain (`cargo check -p
floom --target aarch64-unknown-linux-ohos` → 0 error; UNVERIFIED on-device at
runtime).** `fontique` (via `parley`) discovers system fonts through
`fontconfig` on Linux. OpenHarmony has **no** `fontconfig`, so on an OHOS
target the `Collection` is empty and text renders with zero glyphs.

`crates/floom/src/platform/ohos_font.rs` (`#![cfg(target_env = "ohos")]`) injects bundled
fonts into the global `FONT_CONTEXT` collection right after it is created
(`crates/floom/src/text/layout.rs` `LazyLock`):

- `register_bundled_fonts(&mut Collection)` reads each path in
  `BUNDLED_FONT_PATHS`, wraps the bytes in a `Blob` (`Arc<Vec<u8>>`, which
  coerces to `Arc<dyn AsRef<[u8]> + Send + Sync>`), calls
  `Collection::register_fonts(blob, None)`, and assigns the first three
  families discovered to the generic `SansSerif` / `Serif` / `Monospace`
  families via `set_generic_families`.
- `BUNDLED_FONT_PATHS` is an **empty placeholder** today — the actual
  `.ttf`/`.otf` files must be bundled into the HAP (e.g. as `rawfile` resources
  extracted to an on-device path by an ArkTS bootstrap step) and the paths
  filled in. Until then the function is a safe no-op; text only renders once
  the fonts exist.

`fontique` is reached through `parley::fontique::{Blob, Collection, FamilyId,
GenericFamily}` (it is a transitive dependency, not a direct `floom` lib dep).
Because the whole module is `cfg(target_env = "ohos")`, host and other-platform
builds are untouched by it.

## Packaging: macOS / Linux build + Vulkan link (#114)

`cargo-ohos-app` upstream is **Windows-only**: its `discover_hvigor` step
hard-codes `hvigorw.bat` (the Windows wrapper); on macOS/Linux the Hvigor
wrapper is the extension-less `hvigorw`. The `harmony-app-rs-patch` deliverable
fixes this; the minimal change is:

- **`discover_hvigor`** — replace the `hvigorw.bat` lookup with a
  `target_os`-aware choice: `hvigorw.bat` on Windows, `hvigorw` elsewhere. (The
  wrapper script already exists in the OHOS SDK `toolchains` directory on every
  platform; only the name differs.)
- **`package`** — invoke the wrapper via `Command::new(hvigorw)` (no `.bat`
  suffix), passing `--mode module -p product` as today.

Until that patch is applied, macOS/Linux users cannot drive the HAP build
through `cargo-ohos-app` at all. (No real-device/HAP `cargo build` was run in
this repo — `cargo check` only type-checks and does not link, so the linker
gaps below are still open.)

### wgpu / Vulkan surface link (#114)

A real HAP `cargo build` (not `check`) must link the OHOS Vulkan surface
extension so the GPU backend can create a `VkSurfaceKHR`:

- Ensure `libvulkan.so` is present in the OHOS sysroot (it is, in the DevEco
  native SDK); wgpu's `ash` loader resolves `vkGetInstanceProcAddr` against it.
- Enable the `VK_OHOS_surface` surface extension in the wgpu/ash build for the
  `aarch64-unknown-linux-ohos` target (the `ohos` feature on `ash` / wgpu's
  Vulkan backend) so `vkCreateSurfaceOHOS` is available.
- If floom links wgpu statically into `libentry.so`, confirm the N-API
  registration (`napi_register_module_v1`) and the winit C-ABI entry
  (`export_ohos_winit_app!`) both survive the final link (see the N-API TODO
  list above).
