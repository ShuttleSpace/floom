# Floom 1.0 Launch Milestone

> **范围**：把 floom 从 `0.2.0` 推到**可对外宣称的工业级 1.0**。这是发布治理文档，与 [`release-policy.md`](release-policy.md) 并列（该文件定义"一次发布要过什么门"，本文件定义"从现在到 1.0 要做完什么"）。
> **依据**：七维竞品评估见 [`competitive-analysis.md`](competitive-analysis.md)（20 个项目 × 7 指标 + 13 条"工业级"门槛）。本文件把其 §8 门槛与 §6 借鉴清单转成可勾选、可跟踪的任务。**第七维度（SDK 体积 / 运行时 CPU·内存·GPU / 渲染·执行性能）是本库额外的硬性评价要求**，见 §0 的 G11–G13 与 WS-3。
> **口径**：`- [ ]` 未开始 / `- [x]` 完成。每条给出**可验证的退出判据**（命令或产物），避免"感觉做完了"。
> **负责人**：`<owner:?>` 为占位，指派后替换。

**目标（一句话）**：floom 1.0 = **锁定三套 ABI + prelude/widgets**、**至少 3 个平台从 gated 推到 tested（含 1 个移动端）**、**补齐开发者表面（llms.txt / CLI / 热重载 / 可视化回归进 CI）**、**守住资源效率与性能预算（体积 / CPU / 内存 / GPU / 帧与分配）**、**生态与文档收口**，并通过 [`release-policy.md`](release-policy.md) 的 6 步发布门禁。

## 4. WS-3 — 资源效率与性能（G11, G12, G13；本库硬性要求）

> 这是本库**额外的评价要求**：`SDK 体积尽量小`、`运行时 CPU/内存/GPU 占用尽量少`、`渲染/执行性能尽量高`。
> 详细竞品对标见 [`competitive-analysis.md`](competitive-analysis.md) §9。**原则：靠"预算 + 回归门禁"守，不靠删功能达成**（见 §9 非目标）。
> 现状基线（`docs/release-policy.md:89-160`，本机 macOS 26.6.2 / M4 Pro）：
> - 体积：headless floor `floom-native-plugin` **485,904 B (≈0.5 MiB)**；`floom-showcase` 12,488,476 B (11.9 MiB)；`floom-window --features real` 11,626,912 B (11.1 MiB)。"增长 >10% 即问"已由 `just gate size` 强制（WS-3.2，2026-11-09），基线为 `docs/superpowers/benchmarks/floom-2-size-baseline.json`（3 档、10%、已签入）。
> - 空闲：`frames=2`/8s、`redraws_requested=3`、CPU `0.15 s`（0.5% 核），`about_to_wait` ~75 次；`floom-app/tests/idle.rs` 与 `DamageRegion`（≥8 脏矩形溢满帧）支撑。
> - 性能：11 个 Criterion bench（`release-policy.md:108-120`）；`scripts/check-perf-budgets.sh` 管 10% 热基准（best-of-N），整套 20% 人工。**10% 门禁已恢复**（WS-3.1，见下）。
> - **已修复（WS-3.1，2026-11-09）**：`check-perf-budgets.sh` 引用的 `docs/superpowers/benchmarks/floom-2-budget-baseline.json` 曾在 `e037fdb2` 被归档、又在 `d1ac74cd`「relocate archived planning docs to external floem-archive」时移出仓库（本机 `../floem-archive/` 同样不存在），脚本因此 `FileNotFoundError`。完整文件仍在 git 历史 `5f4cbcfd`（3,140 B、`schema 1`、`threshold_pct 10.0`、9 条 budgets、`generated 2026-09-19`），已按 WS-3.1 原样恢复（sha256 `cc47ac3a…` 与历史一致），并给脚本补了"基线缺失 → 明确报错 + `exit 2`"分支。实跑：9 条预算 best-of-2 全绿（`exit 0`）、故意改坏一条 median 时 `exit 1`、基线移走时 `exit 2`。**注意**：`--update` 仍会先 `json.load` 现有基线，不能用来从零生成。

- ❌ 为覆盖率而支持全部 8 个 gated 平台到 tested（1.0 目标 ≥3 含 ≥1 移动端即可，其余诚实标 experimental）。

   - **口径冲突先解**：`release-policy.md` 第 4 步要求 `cargo fmt --package=<touched>`（"never `--all`"），但 `gate.sh fmt_check` 跑 `cargo fmt --all --check`。**发布以 `release-policy` 为准**：门禁 `fmt` 绿之外，另按 touched-package 复核一次，并在 WS-2.1 记录该冲突。
2. 设备 job：`just gate android ios windows ohos` 对应 targets 表状态一致（tested 的必须绿，experimental 的必须诚实标注）。
   - **check 名以 `scripts/gate.sh --list` 为准**：`android`/`ios`/`windows`/`ohos`（**无 `-check` 后缀**——那是 `.github/workflows/ci.yml` 的 job 名）。`gate.sh` 只按 `has_check <name>` 匹配，传错名字会静默跑全量门禁，正是"把 skip 读成 pass"的同类失败。
3. `cargo test -p floom --test docs_parity` 7/7 绿（文档与树不漂移）。
4. `just gate deny` 绿（WS-2.4 新增的许可证 check）；`cargo deny check` 直接跑同样绿。
5. **资源效率与性能（WS-3）**：
   - `just gate size` 绿：3 档体积记录、headless floor 增长 <10%、per-feature-bundle 预算内。
   - `just gate perf` 绿：基线 JSON 存在且 `scripts/check-perf-budgets.sh` 10% 阈值不超、整套 20% 人工比对有书面理由。
   - 内存 RSS/峰值、GPU 时间/显存、逐帧分配计数在预算内（新增 `just gate resources` 或并入 `perf`）。
   - Metal 空闲冒烟：`FLOOM2_WINDOW_IDLE=1 FLOOM2_WINDOW_IDLE_SECS=8 cargo run -p floom-window --features real` → `frames=2`、CPU ≈0.5% 核。
6. release notes 记录：四判据 + 体积（headless floor / showcase / window）+ 测试数 + 各平台状态 + 已知 experimental 项 + 延迟数字（热重载，若属 1.0.x 则标"未测"）+ **帧预算 / 内存 / GPU / 逐帧分配基线数字**。
7. tag `1.0.0`，填 `docs/ecosystem.md` 兼容矩阵，发布对外公告（含 `llms.txt` 与 `breaking-changes` 链接；**仅宣称必达门已过的能力**）。
