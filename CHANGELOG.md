# Changelog

## Unreleased
- `floom-plugin-nativeview` builds **real web views** instead of a blank `NSView` for every request. `create` used to ignore its `kind` argument — the provider answered "anything" with a view that drew nothing, which is the exact failure the provider registry was built to stop one layer up. It now maps `FLOOM_NATIVE_KIND_WEB` to a `WKWebView` and **refuses every other kind with a message that names it**, so a camera request gets a stated refusal rather than a rectangle indistinguishable from a view that was never asked for. Three things had to change with it. Views are kept **per slot** rather than in one global `g_view`: a scene can hold two participants at once, and the singleton let the second `create` steal the first one's handle — invisible while every view was blank, a leaked web view the moment it is real. `capabilities` became honest: `input.capture` and `focusable` are true because a web view's links, scrolling and text fields need both, where the old answer (passthrough, unfocusable) described something that looks interactive and behaves like a picture. And `floom_nativeview_load_url(slot, url)` is a new entry point on the plugin's own ABI rather than a provider verb, because the provider ABI describes a composited rectangle and what a page displays is not part of that contract. URL validation requires a non-empty scheme — measured, because `NSURL URLWithString:` happily parses `"not a url"` into an object with no scheme, and handing that to WebKit produces a blank page rather than a refusal. Two real defects surfaced on the way: `NativeSlot` is not `#[repr(C)]`, so passing it straight across `extern "C"` was a `SIGSEGV` (the ABI's `FloomNativeSlot` is what crosses); and `WKWebView` asserts the main thread, where the old plain-`NSView` test happened to work on a spawned thread — the test now prints why it cannot run and the creation path is covered by `examples/native_view.rs`, which runs on the main thread like an app. Teeth checked: disabling the refusal branch makes the example panic at `bind` with `this plugin builds web views only: Overlay`. Still missing: the **JS ← Rust bridge** (`addScriptMessageHandler` needs an Objective-C `WKScriptMessageHandler` and a decision about the Rust-side receiving shape), and camera, which needs a Java half — `hasCode="false"` leaves no Activity to request `CAMERA` from and no `SurfaceHolder.Callback` implementation.
- `floom-plugin-tray` puts an icon in the system tray with a menu, on **all three** desktops, with no `tray-icon` dependency: that crate hard-depends on `winit` 0.30, `tao`, `eframe` and `gtk`, which would pull a second `winit` beside the `floem-winit` 25.10.0 fork and drag GTK in on Linux. Each arm owns its object instead — macOS an `NSStatusItem` with an `NSMenu` whose action target is a `define_class!` class, Windows `Shell_NotifyIconW` over a message-only window this crate creates plus a `HMENU` it shows from that window's procedure, Linux an `org.kde.StatusNotifierItem` and `com.canonical.dbusmenu` pair exported over zbus's blocking API (no tokio). Three decisions make one API out of them: the icon is a **text label**, because a menu-bar title, a tooltip and an SNI `Title` are the only thing all three render without shipping assets; menu ids are confined to `1..=0xFFFF` by shared validation, because `0` is how Win32 reports a dismissed menu and the upper bound is where `WM_COMMAND`'s command word ends; and the menu is static — no label updates, submenus, checkboxes or left/right distinction, each of which is three shapes and therefore a decision rather than a flag. The crate runs no loop: it fills a queue and `Tray::events()` drains it, which is what keeps a tray from owning the app. Dropping the `Tray` removes the icon. Mobile refuses by name — a phone has no tray, and the way to reach a user who is not looking is a notification. Verified here: the macOS example creates and removes a real status item without aborting (an ObjC exception aborts rather than panics, so that call has teeth) and the non-main-thread refusal, id/label validation have unit tests; the Windows and Linux arms are compile-checked for their targets and the Linux one also compiles and tests natively in the `plugins` CI job. **Not** verified: clicking a menu row (needs a human — the gallery's `device::show_tray` / `device::poll_tray` pair exists for that) and any Windows or Linux runtime.
- The capability plugins moved out of the SDK workspace into `crates/ecosystem/plugins/`, their own workspace. The SDK now ships **no** plugin: `cargo test --workspace`, `cargo clippy` and `cargo fmt --all` at the root do not build one, and an application adds the ones it wants by path or by version. The layer rule did not move with them — `scripts/check-architecture-deps.sh` loads that workspace's metadata as a second source, so a plugin's "no dependency above L5" edge is checked whether or not an example happens to link it, and a plugin missing from `LAYERS` still fails. Coverage followed the code rather than being assumed: `scripts/gate.sh` grew a `plugin_manifest_check` that fails when the workspace holds a plugin no gate list names (the lists are hand-written, the members are a glob), `plugins` became one `cargo clippy --workspace --all-targets --all-features -- --deny warnings` inside that workspace, the android/ios/windows checks take `--manifest-path`, and CI gained a `plugins` job on both runners (each host compiles a different set of `cfg` arms). `examples/floom-capabilities` reaches across the boundary by path, the way it already reaches `floom-ui`. The registry list in `docs/plugin-catalog.md` §6 shrank from eight places to six and says why.
- vello applies **filter scopes** instead of counting them as skipped. A `FilterPush`/`FilterPop` pair used to draw its contents sharp with a `filters_skipped` tick, because vello rasterises once at the end of the whole scene and there is no point mid-walk at which "this scope's content, as pixels" exists. The scope's span is now rendered as its own offscreen pass, read back, blurred, and drawn back over the content it covers. Three decisions carry it: the blur kernel moved to `floom_renderer::blur` and **software now uses the same function**, so a `Filter::blur(8.0)` looks the same on both backends rather than being two implementations free to drift; the scoped pass re-walks only the scope's nodes, so the blur cannot smear across the scope's boundary the way blurring the frame and masking would; and the result is drawn opaque over its own source rather than blended with it, which would double every edge. `filters_drawn` counts what really blurred and `filters_skipped` keeps what could not (an empty scope, a failed readback) — two numbers rather than one, because "a filter ran" and "a filter was dropped" are different facts. `RendererCapabilities.filters` is now `true` on the GPU presenter. **Backdrop filters remain unimplemented and still count**, and the reason was corrected rather than left as folklore: the blocker is not "the API renders one scene per call" but that vello **clears the target on every pass** — measured, with two passes into one texture leaving only the second. That is why a scope (renderable whole) became possible while a backdrop filter (which needs the prefix to survive into the suffix) did not. Two GPU pixel tests cover the new path and were checked for teeth: disabling the filter pass turns only the filter test red. `Path`/`GlyphRun` shadows are unchanged and are not "skipped" — `SceneNode::Path` has no `shadow` field, so there is no request to drop.
- The vello GPU path has pixel-level regression tests. `VelloGpuPresenter::render_offscreen(scene, resources, width, height) -> Option<Vec<u8>>` rasterises through the **same `encode` path a window uses** into an offscreen texture and reads the RGBA back, so what the tests exercise is the real encoder rather than a second implementation that could drift from it. `crates/floom-renderer-vello/tests/gpu_pixels.rs` then asserts about **where the ink is**, not about counters: an empty scene is transparent and a filled rect is not; a clip crops the ink at its own edge while an unclipped mark behind it survives; a shadow puts ink outside the rect it belongs to. Counters were the only evidence the GPU path had, and they say what was asked for, not what was drawn — a clip applied twice moves the boundary and every counter stays green, which is exactly the class of bug `d4827c5b` fixed. Teeth verified rather than assumed: replacing the encode with an empty scene turns all four red, and removing only the clip marker turns only the clip test red. The tests are `#[ignore]`d because they need a real adapter; the gate gained a `gpu` check that compiles the whole `gpu` feature on **every** machine (that feature was never compiled by any check before, which is how two `--deny warnings` failures survived in it) and prints what actually happened — "4 pixel tests ran and passed", or "skipped — no GPU adapter on this machine". A skip is never counted as a pass, and `FLOOM_REQUIRE_GPU=1` turns a missing adapter into a red check for release runs. Run them yourself with `cargo test -p floom-renderer-vello --features gpu -- --ignored`.
- Native-view providers are registered **by kind**, and an unclaimed kind is refused. `WidgetHost::set_native_provider` is gone; `register_native_provider(provider, kinds) -> Result<(), NativeError>` makes the host state exactly which `NativeViewKind`s a provider can draw, and `floom_native::registry::NativeProviderRegistry` routes every participant to the provider that claimed its kind. One provider may claim many kinds — an OS host owns its views and cannot be duplicated per kind — but one kind has exactly one provider, and a second claim is `Err(KindRegistered(kind))` at registration rather than a silent last-wins at bind. A kind nobody claimed is `Err(NoProvider(kind))` at bind, naming the kind. The catch-all this removes was not hypothetical: the desktop bridge's default factory is `|_, mtm| NSView::new(mtm)`, so it "succeeded" at building a view it never drew for *any* kind, and a `Custom("camera")` request got a blank rectangle — indistinguishable, as `WidgetHost`'s own docs say, from a view that was never asked for. Lifecycle enforcement stays per provider (one `NativeViewController` each, so bound/frozen/mode invariants are unchanged and every backend gets them for free); focus became registry-wide rather than per provider, because IME ownership must not become one owner per provider. `reconcile_clipping` now asks for capabilities of the participant's own kind instead of one global `capabilities()`. `floom-probe` declares `Video` only, the one kind it mounts. Two honest gaps recorded rather than papered over: the desktop bridge's kind claim still comes from the caller (`NativeViewHost::with_factory` does not state what it can build, so `create_view` cannot yet refuse a kind it cannot draw — that needs a real webview factory), and `floom-native`'s `NoProvider`/`KindRegistered` are Rust-only error variants since the C vtable flattens errors to free-form strings.
- `floom-plugin-share` and `floom-plugin-notifications` now have macOS arms, and the platform layer gained runtime window control. Share's is `NSSharingServicePicker` anchored to the key window's content view — AppKit has no window-less picker, so the anchor is `NSApplication.keyWindow`, the same choice Flutter's macOS implementation makes; the picker is held in a thread-local so it outlives the call that opened it without leaking one per share, and an off-main-thread call says so instead of aborting. Notifications reuse the iOS arm (`UNUserNotificationCenter` is the same framework on both) with one macOS-only check first: `UNUserNotificationCenter.currentNotificationCenter` raises an Objective-C exception that Rust cannot catch when the process has no bundle identifier, so an unbundled `cargo run` gets `Err` naming the bundle instead of a crash — and a host test asserts exactly that, because the test binary is itself unbundled. Windows and Linux refusals now name the door rather than saying "mobile only": WinRT's `DataTransferManager` + `IDataTransferManagerInterop::ShowShareUIForWindow` for share and an app identity for toasts, and for Linux the fact that no cross-desktop share API exists and that a notification daemon speaks D-Bus (`org.freedesktop.Notifications`). Window control is `Window::control(WindowCommand)` — resize, move, fullscreen, minimize, maximize, always-on-top, decorations, visibility, focus — with a defaulting `Err` for backends that have no window manager to ask (a terminal grid, a browser canvas) and a real implementation in the winit backend. `Ok` means the windowing system took the request; the size a window actually ends up with still arrives through its resize event, which is why the adapter does not update the size it reports from the request.
- Add `floom-plugin-secure-storage` (from `docs/plugin-usage-priority.md`, the usage-ranked pass that found it above `image_picker` and outside the publisher-scoped catalog): secrets in the OS's own protected store — `SecureStorage::open(service)`, then `get` / `set` / `remove`. It is deliberately not `prefs` under another name: `prefs` stores plaintext in the OS's preferences store, which is the thing this crate exists to avoid, and the crate doc draws that line in a table. Four arms, none of them a file of plaintext: the Apple keychain (`security-framework`'s generic-password item, `service` → `kSecAttrService`, key → `kSecAttrAccount`) with a real host roundtrip test through the actual keychain; Android's Keystore holding an AES-256-GCM key with the ciphertext in `SharedPreferences` (framework classes only — `EncryptedSharedPreferences` would need a Gradle dependency the `hasCode="false"` apps cannot add), and `commit()`-not-`apply()` for the same reason `prefs` chose it; Windows DPAPI (`CryptProtectData`) over a length-prefixed file in the user's config directory, written temp-then-rename; Linux libsecret through `secret-tool`, the `open-url` shape. `get` returns `Result<Option<String>, String>` and the split is the API: `Ok(None)` is *absent*, `Err` is *the store could not be asked* (a locked keychain, an invalidated Keystore key), because reporting a broken store as "no secret here" is the one wrong answer worth distinguishing. The Windows file format and the Android hex codec live in modules compiled on every host so their parsers are tested where they can run — a corrupt store has to be an `Err`, never a silently empty one. Linux refuses a value ending in a newline rather than storing a changed secret. Registered in the eight places the catalog lists, including the gate's Windows list because its Windows arm is the product.
- Add `floom-plugin-mdns` (from `docs/plugin-catalog.md`, batch 5 / C6): who on this network is serving `_http._tcp` — mDNS / DNS-SD discovery, `browse(service_type, duration) -> Vec<Service>`. **No platform arms at all**, and that is the design: mDNS is a wire protocol (RFC 6762/6763), so one implementation serves every target the way `std`'s sockets serve `network-info`'s `local_ip` — `mdns-sd` (pure Rust, no C library, no Avahi/mDNSResponder dependency) carries the platform-specific socket code, and the gate's android/ios/windows checks now compile it for the targets a host build never would. The API is a bounded window, not a stream: send the questions, collect what resolves before the deadline, return one snapshot — a re-resolved instance replaces its earlier answer and a removed one leaves the result, so the snapshot is *as of* the deadline, the only honest claim a local-network census can make. Empty is "nobody answered in the window", a real answer rather than a failure; the Android caveat is named rather than papered over (`WifiManager.MulticastLock` needs `CHANGE_WIFI_MULTICAST_STATE`, which the `hasCode="false"` example apps do not declare, so an empty result on a phone can mean filtered multicast — the follow-up arm is the JNI bridge acquiring the lock). Validation refuses a name that is not a wire service type before any packet is sent. The host test is a real roundtrip through the crate's own daemon: register an instance on one daemon, discover it through `browse` on another — the same path two processes on a LAN take. Deliberately not here: advertising, continuous monitoring, unicast DNS-SD, sub-types. The gallery gained a `mdns::browse` action (two seconds against `_http._tcp.local.`), and the report prints an empty result as an answer.
- Add `floom-plugin-background-work` (from `docs/plugin-catalog.md`, batch 3 / A8, which merged `android_alarm_manager_plus` + `workmanager`): ask the OS to bring this app back at a time. Writing the arm found the honest narrowing — the `hasCode="false"` example apps have no Java classes, which closes every Flutter-shaped door at once (an alarm callback needs a `<receiver>`, WorkManager needs a `Worker`, iOS `BGTaskScheduler` needs an ObjC handler — the Shape-B native half). The one primitive that needs no Java code at all is an `AlarmManager` alarm whose payload is a `PendingIntent` starting the activity itself: `schedule_app_launch` — the app's own lifecycle is the callback, visibly. `Ok` claims the ask was accepted, and the alarm is the inexact `setAndAllowWhileIdle` (Doze-tolerant, no permission) rather than quietly requiring `SCHEDULE_EXACT_ALARM`; a past time fires immediately, per the platform. iOS's refusal names what the system can do instead (notifications with triggers), the desktops' name whose job the work is (launchd/systemd timers/Task Scheduler). The notifications plugin's Android delayed arm — which refused because posting now at the wrong time is worse than not posting — now points at the three-line recipe in this crate's docs: schedule the launch, persist the owed notification, post immediately on startup. This closes batch 3: A7 and A8, and with them every Tier-A catalog entry is implemented.
- Add `floom-plugin-network-info` (from `docs/plugin-catalog.md`, batch 3 / A7): the current Wi-Fi network's name, and this device's address on it — two functions instead of one struct, because `network_info_plus` conflates two questions with different privacy profiles. `local_ip()` is one implementation for every platform (std's UDP-connect route lookup sends nothing and works everywhere); `wifi_info()` answers per platform, and its `None`/`Err` table is in the crate doc because the interesting states map differently: Android's `<unknown ssid>` is a `None` (the platform answering "not willing" since API 27 without granted location — an SSID is a location), Apple's NULL is an `Err` naming the entitlement. **The finding the batch was predicted on, confirmed and harder than predicted**: on this macOS host, Wi-Fi verifiably associated (802.11ac, channel 149, default route on en0), `CNCopyCurrentNetworkInfo` returns NULL anyway and the OS redacts the SSID from `ipconfig`/`networksetup` output too — an unsigned process does not get its own network's name, period. The arm's `Err` is the correct answer, recorded with the observation. Linux and Windows name their doors (NetworkManager D-Bus, `WlanQueryInterface`) rather than shipping unreachable arms.
- Add `floom-plugin-wakelock` (from `docs/plugin-catalog.md`, batch 2 / A6): keep the display awake while the app is in the foreground — and only the display; the crate does not touch CPU or network idle policy. Android sets `FLAG_KEEP_SCREEN_ON` (a window flag, not a wake lock — no permission, and the ask is scoped to the app's visible window, which is exactly the guarantee the crate documents); iOS toggles `idleTimerDisabled`; macOS holds an `IOPMAssertionCreateWithName` assertion named for the crate — visible in `pmset -g assertions` — with the ID mutex-guarded so the second enable is a no-op rather than a leaked assertion; Windows uses `SetThreadExecutionState`, whose thread-scoping the arm is honest about: releasing from a different thread than the acquire returns an `Err` naming that, rather than the documented silent no-op. Linux has no cross-desktop API and says so. `keep_screen_on` is a true launch — `Ok` claims the OS accepted the ask — and `is_keep_screen_on` reads the OS's truth back where one is readable (window flags, the timer property, the held assertion) and reports the crate's tracked ask on Windows, where querying the state is not possible without changing it. The macOS arm has a real acquire/idempotence/release roundtrip test through the actual IOKit calls in an ordinary host test.
- Add `floom-plugin-prefs` (from `docs/plugin-catalog.md`, batch 2 / A5): the OS's own key-value store for user preferences — `SharedPreferences` on Android, `NSUserDefaults` on Apple, a percent-encoded `key<TAB>value` file in the config directory on Linux and Windows (the same decision Flutter's own `shared_preferences_linux`/_windows made). The crate doc opens with the split from `floom-persistence`: persistence is a backend you hand a path to for session state and snapshots; prefs *is* the "where", for settings that outlive every session. `set` promises *stored*: Android uses `commit()` (synchronous) not `apply()` — an `Ok` from `apply()` would claim a write that may not have happened; the file arm writes temp-then-rename so a reader never sees a half-written store. The Apple arm has a real native roundtrip test through `NSUserDefaults` in an ordinary host test (a selector typo fails in CI, not in a user's app), whose cleanup found `removePersistentDomainForName:` is an *instance* method — the header settles what an earlier draft got wrong by sending it to the class. The `floom-capabilities` gallery gained the one reading that proves persistence: a `prefs` row counting recorded launches (written by an action, read by the row — split along the gallery's readings-don't-change-the-world line), verified cross-process by writing with `defaults` and reading it back in the next run.
- Add `floom-plugin-file-dialog` (from `docs/plugin-catalog.md`, batch 2 / A3): ask the user for a path — open, save-as, pick a directory. The other implementation half of the handoff doc's C4 decision. `Ok(None)` is the user cancelling and `Err` is the system failing — the distinction is the API, and the gallery's report keeps all three outcomes (chosen / cancelled / refused) visibly different. macOS answers through `NSOpenPanel`/`NSSavePanel`; Linux through `zenity` falling back to `kdialog` (the `open-url` shape: spawn the desktop's own tool); Windows through the classic `GetOpenFileNameW`/`GetSaveFileNameW` + `SHBrowseForFolderW` pair with `OFN_NOCHANGEDIR` always set — the comdlg32 dialogs silently move the process's cwd by default, and a library may not. **Android and iOS refuse precisely**, the `share_files` precedent: a phone picker's answer arrives as an activity result or a delegate callback, and the platform layer exposes no channel for either — the refusal names the plumbing, which is platform-layer work. Two findings recorded in the crates: `NSOpenPanel` cannot even be *created* outside an `NSApplication` context (AppKit throws, Rust cannot catch foreign exceptions — the attempted selector-resolution test aborted, so the arm's honest host coverage is compilation plus the gallery button in a real app), and no filters yet because every platform names them differently and v1 answers the capability question without choosing whose vocabulary becomes the crate's. It also gained the one query a caller genuinely needs, settled along with C4: `pub const SUPPORTED: bool`, generated by `dialog_arms!` from the same target list as the three arms, because `pick_file` cannot serve as its own probe — on a target that has a dialog the call puts a modal on screen and waits for a human.
- Add `floom-plugin-open-url` (from `docs/plugin-catalog.md`, batch 1 / A2): hand a URL to the OS's own routing — `Intent.ACTION_VIEW` on Android (no chooser: the default handler *is* the point, unlike share), `openURL:options:completionHandler:` on iOS with a null completion block (the `BOOL` return is this crate's answer; a completion block would be a second one), `NSWorkspace openURL:` on macOS, `xdg-open` on Linux, `ShellExecuteW` on Windows. This is the implementation half of the handoff doc's C4 decision — the `OPEN_URL` capability bit was deleted because nothing implemented it, and C4 has since been settled (`docs/plugin-catalog.md` §8.3): the bit does not come back. A `Capability` bit is answered by the platform adapters, and no adapter can see whether a plugin is linked (`floom-platform*` depends on no plugin, and must not), so the honest forms are the compile-time one ("is this crate in your `Cargo.toml`") and the runtime one (the call's `Err`). `Ok(())` claims exactly one thing: the OS accepted the request — the crate documents that as the "true launch" category, and refuses to claim a window opened. Scheme validation fails before dispatch so a typo reaches the caller as one reason instead of five platform errors. The gate gained a `windows` check (`scripts/gate.sh`): no CI job compiles a Windows arm, and an arm no check ever compiles is how `floom-plugin-vibration`'s iOS half kept two edition-2024 errors — `paths` and `open-url` are the first plugins with real Windows arms, and now something compiles them.
- Add `floom-plugin-paths` (from `docs/plugin-catalog.md`, batch 1 / A1): where this app may write — application support, documents, cache, downloads, plus Android's app-scoped external storage as its own function because it exists on exactly one platform. Every arm is a real read: Android via `Context` through the platform JNI bridge, iOS/macOS via `NSSearchPathForDirectoriesInDomains` (a Foundation *function*, declared through FFI after `msg_send!` to `NSFileManager` was refused by objc2's runtime check), Linux/Windows via `dirs`. No host-inert arm exists at all — on the desktop the platform conventions *are* the source of truth — so the `floom-capabilities` gallery gained its first host-answered row (`= paths` on a laptop), and the gallery's host-honesty invariant gained a `Row::desktop_real` distinction to keep it exact: it forbids unmeasured values, not desktop values. Downloads is `None` on Apple platforms rather than redirected at Documents, because redirecting would answer a different question.
- Add `floom-plugin-package-info` (from `docs/plugin-catalog.md`, batch 1 / A4): the running app's own identity — name, bundle id, version, build number — read from `PackageManager` on Android and `NSBundle` on iOS **and macOS**. Unlike the nine mobile-only plugins, its Apple arm compiles under an ordinary host `cargo test`, so part of the native code is exercised by the host gate. Fields are `Option<String>` for the reason battery's `level` is: Linux and Windows have no answer today, and `Some("")` would be a value nobody measured. Registered in all eight places the catalog lists (workspace members, default-members, gate clippy + plugin lists, architecture gate, layer table, CI android/ios checks), and wired into the `floom-capabilities` gallery, whose module doc had recorded `app_info` as a dropped row waiting for exactly this crate. The gallery reports the macOS bare-binary case as `Error` — "the platform has it, this invocation cannot serve it" — rather than `Absent`, which would claim macOS lacks the capability.
- Import the satellite projects into this repository under `crates/ecosystem/`: `floom-ui` (the Material / Cupertino / Fluent kit, previously the misspelled sibling repo `flome-ui`, imported with its 17-commit history via `git subtree`), `floom-editor`, and `flameo`. Each stays its own nested workspace and is excluded from the root, so `cargo test --workspace` is unchanged; `examples/{custom_keymap,widget-gallery}` are repointed at the in-repo editor. See `docs/ecosystem.md`.
- Rename the vendored OHOS backend off the `tgui` namespace: `crates/vendor/tgui-winit-ohos` → `crates/vendor/floom-winit-ohos` (`tgui-winit-ohos` → `floom-winit-ohos`, `tgui_winit_ohos` → `floom_winit_ohos`). Because a `[patch.crates-io]` entry must keep the name of the package it replaces, the fork becomes a plain path dependency in `[workspace.dependencies]`. The rename also **fixes a latent OHOS-only bug**: the fork pinned `floem-winit-core` / `dpi` to the git rev while the patched `floem-winit` facade used the vendored copies, so the resolve graph held two `floem-winit-core` and three `dpi` instances and the backend required a different `ApplicationHandler` than the one `floom::Application` implements. `[patch."https://github.com/lapce/winit"]` now pins every member of the fork.
- Reorganise the workspace after the [EpicGames/lore](https://github.com/EpicGames/lore) model. The legacy v1 crates move under `legacy/` with a `floom-legacy-` prefix (`floom_renderer` → `floom-legacy-renderer`, `floom_reactive` → `floom-legacy-reactive`, `floom-test` → `floom-legacy-test`, plus the four renderer backends), vendored third-party forks move to `crates/vendor/` with a per-fork `NOTICE.md`, and `notices/` is added for license compliance. See `docs/workspace-conventions.md`.
